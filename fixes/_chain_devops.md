# Связность цепочки Docker → Traefik → Kubernetes

Проверка «сквозной» логики трёх DevOps-лаб: всё, что лаба использует, должно быть объяснено в ней самой или
в предыдущей лабе цепочки; всё, что понадобится следующей лабе, должно быть создано/объяснено в предыдущей.
Построчная вычитка каждой лабы — в `docker.md`, `traefik.md`, `kubernetes.md`; здесь только стыки между лабами.

Теги:
- **[пробел]** — понятие/команда/файл используется, но нигде раньше в цепочке не объяснено;
- **[наследство]** — следующая лаба рассчитывает на то, чего предыдущая не даёт (файл, образ, настройку, знание);
- **[расхождение]** — одно и то же в двух лабах называется/работает по-разному (порты, имена, версии, env);
- **[дубль]** — тема подробно разобрана заново, хотя уже была в предыдущей лабе (можно заменить ссылкой).

## Стык Docker → Traefik

- **[расхождение] Docker-лаба §3.3/§8.4 vs Traefik-лаба Шаг 2.3 и §14.5** — Docker-лаба явно учит: секреты — не хардкодить в файлы, которые видит сборка/репозиторий, а держать в `.env`/`env_file` (§8.4: таблица «Где хранится / Когда использовать», с явным «секреты и локальные настройки — обязательно в .gitignore»), и отдельно предупреждает про случайное «запекание» секретов (§3.3, врезка «Частая ошибка»). Traefik-лаба сама же перечисляет `.env` в структуре проекта (раздел 4: `traefik-lab/├── .env`), но ни разу его не создаёт и не использует: пароль БД прописан прямо в теле compose-примера — «`db: … environment: POSTGRES_PASSWORD: labpass`» (Шаг 2.3), а на боевом сервере email для Let's Encrypt — прямо в `traefik.yml`: «`email: ваш-настоящий-email@meeymirita.ru`» (§14.5), без `${...}` из `.env`. → Либо убрать `.env` из структуры (раздел 4), раз он нигде не используется, либо, что понятнее и совпадает с уроком Docker-лабы, перенести `POSTGRES_PASSWORD` и e-mail в `.env`/`${VAR}`-подстановку и показать это явно хотя бы один раз в Шаге 2.3 или §14.5 — сейчас лаба фактически противоречит собственному «источнику знаний».

- **[пробел] Синтаксис `host:container:ro` (флаг режима монтирования)** — Traefik-лаба многократно использует третий сегмент после второго двоеточия в volume/bind-mount, например «`/var/run/docker.sock:/var/run/docker.sock:ro`», «`./traefik/traefik.yml:/etc/traefik/traefik.yml:ro`» (Шаг 1.3), и объясняет *зачем* это read-only («🔬 Под капотом: почему сокет монтируется read-only…»), но нигде — ни в Docker-лабе (раздел 6.1 «Тома и данные» даёт только двухсегментный формат `host:container`, без третьего поля режима), ни в самой Traefik-лабе — не проговаривает, что это вообще за третий сегмент в общей грамматике `-v`/`volumes:` (что после второго `:` идёт режим доступа, и что бывает и `rw`). Читатель, который не встречал такую запись раньше, должен угадать формат по контексту. → В Docker-лабе (§6.1, там же где даётся `host:container`) добавить одну строку про необязательный третий сегмент режима (`ro`/`rw`) с примером — тогда к Traefik-лабе это уже «знание», а не «пробел».

- **[расхождение] Версия образа PostgreSQL между Docker-лабой и Traefik-лабой** — Docker-лаба последовательно использует `postgres:16-alpine` (§6.1, §8.2, §8.3, Шаг 2.1) и в §3.6 отдельно объясняет, почему в проекте по умолчанию выбирают более лёгкий вариант образа (alpine/slim) там, где не нужен bash. Traefik-лаба и в стек-таблице (раздел 4: «БД — PostgreSQL 16»), и в коде Шага 2.3 использует полный `image: postgres:16` (без `-alpine`) — при этом никакой особой причины (нужен bash/glibc внутри контейнера БД) в тексте не приведено. → Привести к одному образу, вероятнее всего `postgres:16-alpine` — как в Docker-лабе и как в Kubernetes-лабе (см. `fixes/traefik.md`, вопрос про PostgreSQL 16, и `fixes/kubernetes.md` — там то же самое расхождение уже отмечено на стыке Traefik→Kubernetes; здесь тот же образ ещё и расходится с Docker-лабой).

- **[наследство] Тег `traefik-lab-api:v1`, который берёт Kubernetes-лаба, нигде явно не создаётся в Traefik-лабе** — сервис `api` во всей Traefik-лабе описан только как «`api: build: ./api networks: […] labels: […]`» (Шаг 2.1) — без поля `image:` и без единой команды `docker build -t traefik-lab-api:v1 …`; при `docker compose build` реальный тег образа будет автоматическим (по имени проекта/сервиса), а не `traefik-lab-api:v1`. Строка «traefik-lab-api:v1» в тексте Traefik-лабы не встречается ни разу. → добавить в Traefik-лабу (например, в конец, рядом с рекомендацией «не удаляй `api/`» из `fixes/traefik.md`) явную команду сборки с этим тегом, либо поле `image: traefik-lab-api:v1` у сервиса `api` — иначе на стыке с Kubernetes-лабой первый же шаг там ссылается на артефакт, которого лаба-источник не производит (подробный разбор — в ведении агента по Traefik→Kubernetes).

- **[пробел] Флаг `--scale` используется без объяснения синтаксиса** — Шаг 2.4: «`docker compose up -d --scale api=3`» — Docker-лаба вообще не упоминает `--scale` ни разу; в Traefik-лабе смысл масштабирования как «несколько контейнеров из одного образа» разобран заранее в §0.2 («Именно так работает масштабирование в шаге 2.4: три контейнера API — это три независимых процесса из одного и того же образа»), но сам синтаксис флага (`--scale <сервис>=<N>`, и что для этого у сервиса не должно быть фиксированного `ports:`/`container_name`, иначе поднимется конфликт портов/имён) не объясняется нигде. → Добавить одну строку с разбором флага прямо в Шаге 2.4 (благо явных `ports:`/`container_name` у `api` в этой лабе и так нет, но это стоит явно назвать как условие, а не оставлять неочевидным совпадением).

### Что проверено и в порядке
- Раздел «0. Введение в Docker: с нуля» в Traefik-лабе — не противоречит Docker-лабе, это осознанный дубль «на одну страницу» для тех, кто пропустил Docker-лабу; сама Docker-лаба (раздел 0) честно называет его «ровно одной страницей на весь фундамент» и объясняет, почему Docker-лаба нужна отдельно. Команды и примеры в обоих разделах совпадают дословно (`docker run -d --name web -p 8080:80 nginx`, `docker compose up -d/ps/logs -f/down`).
- `docker compose` (Compose V2, без дефиса) и отсутствие устаревшего поля `version:` — единообразно в обеих лабах.
- Модель volumes/named volume (`pgdata`/`db-data`) и её назначение («данные переживают пересоздание контейнера») — согласованно между Docker-лабой (§6.1) и Traefik-лабой (§0.6, Шаг 2.3).
- Модель сети и DNS по имени сервиса (`db:5432`, `api:3000`) — согласованно между Docker-лабой (§7.2, §8.2) и Traefik-лабой (§0.5, архитектурная схема раздела 3).
- Проброс портов наружу (`-p`) только там, где нужен вход снаружи — единая логика: у Docker-лабы это общее правило (§2.1, §7.3), у Traefik-лабы — прямое следствие (§0.7): наружу пробрасывается только сам Traefik, остальные сервисы — нет.
- Выбор базового образа (`node:20-slim` в Docker-лабе против `node:20-alpine` в Traefik-лабе) — не расхождение: у API из Traefik-лабы нет entrypoint-скрипта на bash (только `CMD`), так что alpine здесь уместен ровно по той логике, которую объясняет Docker-лаба (§3.6) — bash нужен только когда есть entrypoint.sh.
- PID 1 / сигналы / `exec "$@"` — подробно разобраны в Docker-лабе и не требуются в Traefik-лабе, так как её Dockerfile'ы не используют собственные entrypoint-скрипты; отсутствие темы в Traefik-лабе — не пробел, а отсутствие необходимости.
